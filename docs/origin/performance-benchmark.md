# 性能与资源效率测试

这份报告记录 fn-knock 网关与其他产品在同一受控测试环境中的压力测试结果。它用于呈现指定版本、配置和请求模型下的相对表现，不代表第三方认证，也不是对任意硬件或生产流量的性能承诺。

## 结论摘要

在本轮主要对比的 HTTPS 未匹配路由场景中，fn-knock 在吞吐、P99 延迟、单位 CPU 吞吐和内存占用方面均表现更好：

| 指标 | fn-knock | 其他产品 | 结果 |
| --- | ---: | ---: | --- |
| 512 并发吞吐 | 13,026 req/s | 4,642 req/s | fn-knock 为 `2.81×` |
| 512 并发 P99 | 498.68 ms | 573.10 ms | fn-knock 低 `12.99%` |
| 单位 CPU 吞吐 | 2,242 req/s/核 | 1,063 req/s/核 | fn-knock 高 `110.89%` |
| 高压平均 RSS | 153.4 MiB | 325.6 MiB | fn-knock 少 `52.90%` |

关闭回环来源的请求日志后，fn-knock 的吞吐没有显著变化，但高并发 P99、CPU 和内存抖动有所下降，同时不再为这批压力测试请求写入访问日志。

## 测试条件

| 项目 | 设置 |
| --- | --- |
| 测试日期 | 2026-07-31 |
| 发压工具 | `wrk`，8 个线程 |
| 并发级别 | 64、256、512 |
| 主要请求 | HTTPS，请求 Host 为 `loadtest.invalid`，命中未匹配路由并返回 404 |
| 资源采集 | 通过 `pidstat` 统计目标服务进程的 CPU 与 RSS 均值 |
| 环境控制 | 发压端与两个被测服务共享同一套 8 核测试资源；各轮使用相同工具和并发参数 |

这种安排减少了网络路径差异，但发压工具也会竞争 CPU，因此结果反映的是整套测试环境的联合上限，不等于服务在独占硬件或真实公网链路中的绝对容量。

## 吞吐与尾延迟

| 并发 | fn-knock 吞吐 | 其他产品吞吐 | fn-knock 吞吐优势 | fn-knock P99 | 其他产品 P99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64 | 13,529 req/s | 2,992 req/s | `352.14%` | 30.38 ms | 81.52 ms |
| 256 | 12,982 req/s | 4,251 req/s | `205.36%` | 242.29 ms | 272.92 ms |
| 512 | 13,026 req/s | 4,642 req/s | `180.63%` | 498.68 ms | 573.10 ms |

fn-knock 在 64 并发时已达到约 13.5k req/s，继续增加并发没有带来更高的稳定吞吐，主要变化是排队时间和尾延迟上升。其他产品从 256 增加到 512 并发时，吞吐增加约 `9.2%`，P99 则增加约 `110%`。这说明两条路径都已接近各自在该请求模型下的容量拐点。

## 512 并发下的资源效率

| 指标 | fn-knock | 其他产品 | 解读 |
| --- | ---: | ---: | --- |
| 服务 CPU | 5.81 核 | 4.37 核 | fn-knock 多使用 `33.07%` CPU |
| 吞吐 | 13,026 req/s | 4,642 req/s | fn-knock 多处理 `180.63%` 请求 |
| 单位 CPU 吞吐 | 2,242 req/s/核 | 1,063 req/s/核 | fn-knock 高 `110.89%` |
| 高压平均 RSS | 153.4 MiB | 325.6 MiB | fn-knock 少 `52.90%` |

fn-knock 在高并发轮次使用了更多 CPU，但新增的吞吐远高于 CPU 增幅，因此单位 CPU 效率仍然更高。CPU 使用率本身不是越低越好；应结合完成的请求量、尾延迟和错误率一起判断。

## 内存生命周期

| 阶段 | fn-knock | 其他产品 | 其他产品 / fn-knock |
| --- | ---: | ---: | ---: |
| 压测前 | 58.3 MiB | 121.4 MiB | `2.08×` |
| 高压平均 | 153.4 MiB | 325.6 MiB | `2.12×` |
| 历史峰值 | 228.6 MiB | 610.0 MiB | `2.67×` |
| 同轮冷却后 | 132.8 MiB | 201.7 MiB | `1.52×` |

其他产品的历史峰值达到 610.0 MiB。后续复压中还出现 6 次超时，P99 一度达到 1.12 秒；fn-knock 的复压没有出现超时，也没有继续抬高已记录的内存峰值。

短时复压只能观察高水位和初步回收趋势。判断是否存在缓慢增长、碎片化或泄漏，仍需要 30–60 分钟以上的持续负载、稳定请求模型和多轮独立复测。

## 关闭压测请求日志后的变化

对 fn-knock 关闭回环来源的请求日志后，与上一轮启用状态相比：

| 并发 | 吞吐变化 | P99 变化 | 平均延迟变化 |
| ---: | ---: | ---: | ---: |
| 64 | `−4.06%` | `−13.52%` | `+0.67%` |
| 256 | `−0.72%` | `−10.63%` | `−10.08%` |
| 512 | `+0.32%` | `−6.83%` | `−5.03%` |

512 并发下的吞吐差异只有 `0.32%`，可视为测量波动；P99 下降 `6.83%`，CPU 均值下降 `0.96%`，高压平均 RSS 下降 `5.39%`。本轮共发出 593,792 次请求，访问日志新增量为 0 byte。

因此，压测请求日志不是该场景的主要吞吐瓶颈。关闭它的主要价值是减少磁盘写入和资源抖动，而不是显著提高 RPS。生产环境是否记录回环或可信来源请求，应根据审计需求、存储成本和排障方式决定。

## 管理 API 路径仅作参考

本轮还采集了 fn-knock `7998` 管理 API 的 readiness 路径，用于观察控制面的资源位置：

| 路径 | 请求内容 | 吞吐 | P99 | 服务 CPU | 高压平均 RSS |
| --- | --- | ---: | ---: | ---: | ---: |
| fn-knock 网关 `7999` | HTTPS 404、CIDR 判断与路由 | 13,026 req/s | 498.68 ms | 5.81 核 | 153.4 MiB |
| 其他产品 | HTTPS 404 | 4,642 req/s | 573.10 ms | 4.37 核 | 325.6 MiB |
| 管理 API `7998` | HTTP readiness，包含网关状态检查 | 5,157 req/s | 162.46 ms | 2.01 核 | 169.3 MiB |

`7998` 是控制面，readiness 请求与 `7999` 的 HTTPS 网关数据面并不等价。不能用这组数字推断反向代理容量，也不应把管理 API 作为业务流量入口。管理 API 的开放方式和安全边界见 [OpenAPI：开放管理 API 与 AI Agent](/guide/openapi)。

## 如何理解结果

1. **fn-knock 在本轮请求模型中更高效。** 512 并发稳定轮的吞吐约为其他产品的 `2.81×`，P99 更低，单位 CPU 吞吐高 `110.89%`。
2. **增加并发不等于增加有效容量。** fn-knock 在 64 并发附近已达到吞吐平台；继续增加并发主要会提高排队延迟。
3. **内存结果需要长期测试确认。** fn-knock 的短时高压平均值和峰值更低，但单轮测试不能替代长期稳定性验证。
4. **日志策略影响资源抖动和磁盘写入。** 是否关闭某类请求日志，应由运维与审计需求决定，而不是只追求基准测试数字。
5. **控制面与数据面必须分开比较。** `7998` readiness 数据只用于参考，不能与 HTTPS 代理请求直接排名。

## 口径与限制

- 两条主要对比路径都使用 HTTPS、相同 Host 和未匹配路由 404，但响应体不同：fn-knock 约 11.5 KiB，其他产品约 65 B。fn-knock 在响应体更大的情况下仍取得更高吞吐。
- 本轮衡量 TLS、CIDR 判断、路由匹配与网关直接响应处理，不包含具体上游应用，也不能代表任意业务的端到端性能。
- “其他产品”仅指本次被测的特定版本和配置。结果不应外推到该产品的其他版本、部署方式或整个同类产品类别。
- 硬件、内核、TLS 实现、证书、日志设置、连接复用、响应大小和网络路径都会改变结果。评估自己的部署时，应使用相同脚本多轮复测，并同时记录吞吐、P99、错误率、CPU、RSS 和连接数。
- 容量规划应保留余量。若业务重视尾延迟，应在实际请求模型下确定可接受的并发上限，而不是直接采用本页的并发数字。
