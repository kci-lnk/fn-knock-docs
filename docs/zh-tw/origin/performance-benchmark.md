# 效能與資源效率測試

本報告記錄 fn-knock 閘道與其他產品在相同受控測試環境中的壓力測試結果。內容用於呈現指定版本、設定與請求模型下的相對表現，不代表第三方認證，也不是對任意硬體或正式環境流量的效能承諾。

## 結論摘要

在本輪主要比較的 HTTPS 未符合路由情境中，fn-knock 在吞吐量、P99 延遲、單位 CPU 吞吐量與記憶體使用量方面均有較好表現：

| 指標 | fn-knock | 其他產品 | 結果 |
| --- | ---: | ---: | --- |
| 512 併發吞吐量 | 13,026 req/s | 4,642 req/s | fn-knock 為 `2.81×` |
| 512 併發 P99 | 498.68 ms | 573.10 ms | fn-knock 低 `12.99%` |
| 單位 CPU 吞吐量 | 2,242 req/s/核心 | 1,063 req/s/核心 | fn-knock 高 `110.89%` |
| 高負載平均 RSS | 153.4 MiB | 325.6 MiB | fn-knock 少 `52.90%` |

停用回環來源的請求記錄後，fn-knock 的吞吐量沒有明顯變化，但高併發 P99、CPU 與記憶體波動略有下降，同時不再為這批壓力測試請求寫入存取記錄。

## 測試條件

| 項目 | 設定 |
| --- | --- |
| 測試日期 | 2026-07-31 |
| 發壓工具 | `wrk`，8 個執行緒 |
| 併發級別 | 64、256、512 |
| 主要請求 | HTTPS，請求 Host 為 `loadtest.invalid`，未符合任何路由並回傳 404 |
| 資源採集 | 透過 `pidstat` 統計目標服務程序的 CPU 與 RSS 平均值 |
| 環境控制 | 發壓端與兩個受測服務共用同一組 8 核心測試資源；各輪使用相同工具與併發參數 |

此安排可減少網路路徑差異，但發壓工具也會競爭 CPU，因此結果反映整套測試環境的聯合上限，不等於服務在獨占硬體或真實公網鏈路中的絕對容量。

## 吞吐量與尾端延遲

| 併發 | fn-knock 吞吐量 | 其他產品吞吐量 | fn-knock 吞吐優勢 | fn-knock P99 | 其他產品 P99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64 | 13,529 req/s | 2,992 req/s | `352.14%` | 30.38 ms | 81.52 ms |
| 256 | 12,982 req/s | 4,251 req/s | `205.36%` | 242.29 ms | 272.92 ms |
| 512 | 13,026 req/s | 4,642 req/s | `180.63%` | 498.68 ms | 573.10 ms |

fn-knock 在 64 併發時已達到約 13.5k req/s。繼續增加併發沒有帶來更高的穩定吞吐量，主要變化是排隊時間與尾端延遲上升。其他產品從 256 增加到 512 併發時，吞吐量增加約 `9.2%`，P99 則增加約 `110%`。這表示兩條路徑都已接近各自在此請求模型下的容量轉折點。

## 512 併發下的資源效率

| 指標 | fn-knock | 其他產品 | 解讀 |
| --- | ---: | ---: | --- |
| 服務 CPU | 5.81 核心 | 4.37 核心 | fn-knock 多使用 `33.07%` CPU |
| 吞吐量 | 13,026 req/s | 4,642 req/s | fn-knock 多處理 `180.63%` 請求 |
| 單位 CPU 吞吐量 | 2,242 req/s/核心 | 1,063 req/s/核心 | fn-knock 高 `110.89%` |
| 高負載平均 RSS | 153.4 MiB | 325.6 MiB | fn-knock 少 `52.90%` |

fn-knock 在高併發輪次使用了更多 CPU，但新增吞吐量遠高於 CPU 增幅，因此單位 CPU 效率仍然更高。CPU 使用率本身不是越低越好，應與完成的請求量、尾端延遲和錯誤率一併判斷。

## 記憶體生命週期

| 階段 | fn-knock | 其他產品 | 其他產品 / fn-knock |
| --- | ---: | ---: | ---: |
| 壓測前 | 58.3 MiB | 121.4 MiB | `2.08×` |
| 高負載平均 | 153.4 MiB | 325.6 MiB | `2.12×` |
| 歷史峰值 | 228.6 MiB | 610.0 MiB | `2.67×` |
| 同輪冷卻後 | 132.8 MiB | 201.7 MiB | `1.52×` |

其他產品的歷史峰值達到 610.0 MiB。後續重複壓測還出現 6 次逾時，P99 一度達到 1.12 秒；fn-knock 的重複壓測沒有出現逾時，也沒有繼續提高已記錄的記憶體峰值。

短時間重複壓測只能觀察高水位與初步回收趨勢。判斷是否存在緩慢增長、碎片化或洩漏，仍需要 30–60 分鐘以上的持續負載、穩定請求模型與多輪獨立複測。

## 停用壓測請求記錄後的變化

對 fn-knock 停用回環來源的請求記錄後，與前一輪啟用狀態相比：

| 併發 | 吞吐量變化 | P99 變化 | 平均延遲變化 |
| ---: | ---: | ---: | ---: |
| 64 | `−4.06%` | `−13.52%` | `+0.67%` |
| 256 | `−0.72%` | `−10.63%` | `−10.08%` |
| 512 | `+0.32%` | `−6.83%` | `−5.03%` |

512 併發下的吞吐量差異只有 `0.32%`，可視為測量波動；P99 下降 `6.83%`，CPU 平均值下降 `0.96%`，高負載平均 RSS 下降 `5.39%`。本輪共送出 593,792 次請求，存取記錄新增量為 0 byte。

因此，壓測請求記錄不是此情境的主要吞吐瓶頸。停用它的主要價值是減少磁碟寫入與資源波動，而不是顯著提高 RPS。正式環境是否記錄回環或可信來源請求，應依據稽核需求、儲存成本與疑難排解方式決定。

## 管理 API 路徑僅供參考

本輪也採集了 fn-knock `7998` 管理 API 的 readiness 路徑，用於觀察控制面的資源位置：

| 路徑 | 請求內容 | 吞吐量 | P99 | 服務 CPU | 高負載平均 RSS |
| --- | --- | ---: | ---: | ---: | ---: |
| fn-knock 閘道 `7999` | HTTPS 404、CIDR 判斷與路由 | 13,026 req/s | 498.68 ms | 5.81 核心 | 153.4 MiB |
| 其他產品 | HTTPS 404 | 4,642 req/s | 573.10 ms | 4.37 核心 | 325.6 MiB |
| 管理 API `7998` | HTTP readiness，包含閘道狀態檢查 | 5,157 req/s | 162.46 ms | 2.01 核心 | 169.3 MiB |

`7998` 是控制面，readiness 請求與 `7999` 的 HTTPS 閘道資料面並不等價。不能用這組數字推斷反向代理容量，也不應把管理 API 作為業務流量入口。管理 API 的開放方式與安全邊界請參考 [OpenAPI：開放管理 API 與 AI Agent](/zh-tw/guide/openapi)。

## 如何理解結果

1. **fn-knock 在本輪請求模型中更有效率。** 512 併發穩定輪的吞吐量約為其他產品的 `2.81×`，P99 更低，單位 CPU 吞吐量高 `110.89%`。
2. **增加併發不等於增加有效容量。** fn-knock 在 64 併發附近已達到吞吐平台；繼續增加併發主要會提高排隊延遲。
3. **記憶體結果需要長時間測試確認。** fn-knock 的短時高負載平均值與峰值較低，但單輪測試不能取代長期穩定性驗證。
4. **記錄策略會影響資源波動與磁碟寫入。** 是否停用某類請求記錄，應由維運與稽核需求決定，而不是只追求基準測試數字。
5. **控制面與資料面必須分開比較。** `7998` readiness 資料僅供參考，不能與 HTTPS 代理請求直接排名。

## 口徑與限制

- 兩條主要比較路徑都使用 HTTPS、相同 Host 與未符合路由 404，但回應本文不同：fn-knock 約 11.5 KiB，其他產品約 65 B。fn-knock 在回應本文更大的情況下仍取得更高吞吐量。
- 本輪衡量 TLS、CIDR 判斷、路由比對與閘道直接回應處理，不包含特定上游應用，也不能代表任意業務的端到端效能。
- 「其他產品」僅指本次受測的特定版本與設定。結果不應外推至該產品的其他版本、部署方式或整個同類產品類別。
- 硬體、核心、TLS 實作、憑證、記錄設定、連線重用、回應大小與網路路徑都會改變結果。評估自己的部署時，應使用相同 Script 多輪複測，並同時記錄吞吐量、P99、錯誤率、CPU、RSS 與連線數。
- 容量規劃應保留餘量。若業務重視尾端延遲，應在實際請求模型下決定可接受的併發上限，而不是直接採用本頁的併發數字。
