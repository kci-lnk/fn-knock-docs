# 성능 및 리소스 효율 벤치마크

이 보고서는 동일하게 통제된 테스트 환경에서 fn-knock 게이트웨이와 다른 제품을 비교한 부하 테스트 결과를 기록합니다. 지정된 버전, 설정 및 요청 모델의 상대적 성능을 보여 주기 위한 자료이며, 제3자 인증이나 임의의 하드웨어 및 운영 트래픽에 대한 성능 보장이 아닙니다.

## 결과 요약

이번 테스트의 주요 비교 대상인 HTTPS 미일치 라우트 시나리오에서 fn-knock는 처리량, P99 지연 시간, CPU 코어당 처리량 및 메모리 사용량 모두에서 더 나은 결과를 보였습니다.

| 지표 | fn-knock | 다른 제품 | 결과 |
| --- | ---: | ---: | --- |
| 동시 연결 512 처리량 | 13,026 req/s | 4,642 req/s | fn-knock가 `2.81×` |
| 동시 연결 512 P99 | 498.68 ms | 573.10 ms | fn-knock가 `12.99%` 낮음 |
| CPU 코어당 처리량 | 2,242 req/s/코어 | 1,063 req/s/코어 | fn-knock가 `110.89%` 높음 |
| 고부하 평균 RSS | 153.4 MiB | 325.6 MiB | fn-knock가 `52.90%` 적음 |

루프백 출발지의 요청 로그를 비활성화한 후에도 fn-knock 처리량은 크게 달라지지 않았습니다. 다만 높은 동시 연결에서 P99, CPU 및 메모리 변동이 소폭 개선되었고 이 부하 테스트 요청에 대한 접근 로그 쓰기가 완전히 사라졌습니다.

## 테스트 조건

| 항목 | 설정 |
| --- | --- |
| 테스트 날짜 | 2026-07-31 |
| 부하 생성 도구 | `wrk`, 8개 스레드 |
| 동시 연결 수준 | 64, 256, 512 |
| 주요 요청 | HTTPS, Host는 `loadtest.invalid`, 어떤 라우트에도 일치하지 않아 404 반환 |
| 리소스 수집 | `pidstat`로 대상 서비스 프로세스의 CPU 및 RSS 평균 측정 |
| 환경 통제 | 부하 생성기와 두 테스트 대상 서비스가 동일한 8코어 테스트 리소스를 공유했으며 각 실행에서 같은 도구와 동시 연결 매개변수를 사용 |

이 구성은 네트워크 경로 차이를 줄이지만 부하 생성기도 CPU를 함께 사용합니다. 따라서 결과는 전체 테스트 환경의 결합 한도를 나타내며, 전용 하드웨어나 실제 공인 네트워크에서 서비스가 낼 수 있는 절대 용량을 의미하지 않습니다.

## 처리량과 꼬리 지연 시간

| 동시 연결 | fn-knock 처리량 | 다른 제품 처리량 | fn-knock 처리량 우위 | fn-knock P99 | 다른 제품 P99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64 | 13,529 req/s | 2,992 req/s | `352.14%` | 30.38 ms | 81.52 ms |
| 256 | 12,982 req/s | 4,251 req/s | `205.36%` | 242.29 ms | 272.92 ms |
| 512 | 13,026 req/s | 4,642 req/s | `180.63%` | 498.68 ms | 573.10 ms |

fn-knock는 동시 연결 64에서 이미 약 13.5k req/s에 도달했습니다. 동시 연결을 더 늘려도 안정적인 처리량은 높아지지 않았고 주로 대기 시간과 꼬리 지연 시간이 증가했습니다. 다른 제품은 동시 연결을 256에서 512로 늘렸을 때 처리량이 약 `9.2%` 증가했지만 P99는 약 `110%` 증가했습니다. 두 경로 모두 이 요청 모델에서 각자의 용량 변곡점에 가까웠음을 보여 줍니다.

## 동시 연결 512에서의 리소스 효율

| 지표 | fn-knock | 다른 제품 | 해석 |
| --- | ---: | ---: | --- |
| 서비스 CPU | 5.81코어 | 4.37코어 | fn-knock가 CPU를 `33.07%` 더 사용 |
| 처리량 | 13,026 req/s | 4,642 req/s | fn-knock가 요청을 `180.63%` 더 처리 |
| CPU 코어당 처리량 | 2,242 req/s/코어 | 1,063 req/s/코어 | fn-knock가 `110.89%` 높음 |
| 고부하 평균 RSS | 153.4 MiB | 325.6 MiB | fn-knock가 `52.90%` 적음 |

fn-knock는 높은 동시 연결 실행에서 CPU를 더 많이 사용했지만 처리량 증가 폭이 CPU 증가 폭보다 훨씬 컸으므로 코어당 효율도 더 높았습니다. CPU 사용률은 낮을수록 무조건 좋은 지표가 아니며 완료한 요청 수, 꼬리 지연 시간 및 오류율과 함께 판단해야 합니다.

## 메모리 수명 주기

| 단계 | fn-knock | 다른 제품 | 다른 제품 / fn-knock |
| --- | ---: | ---: | ---: |
| 부하 테스트 전 | 58.3 MiB | 121.4 MiB | `2.08×` |
| 고부하 평균 | 153.4 MiB | 325.6 MiB | `2.12×` |
| 기록된 최고값 | 228.6 MiB | 610.0 MiB | `2.67×` |
| 같은 실행의 냉각 후 | 132.8 MiB | 201.7 MiB | `1.52×` |

다른 제품의 기록된 최고값은 610.0 MiB였습니다. 이후 반복 부하 테스트에서는 시간 초과가 6회 발생했고 P99가 한때 1.12초에 도달했습니다. fn-knock 반복 테스트에서는 시간 초과가 없었으며 기록된 메모리 최고값도 더 높아지지 않았습니다.

짧은 반복 테스트로는 높은 사용량과 초기 회수 경향만 관찰할 수 있습니다. 느린 증가, 단편화 또는 누수를 판단하려면 안정적인 요청 모델에서 30~60분 이상의 지속 부하와 여러 차례의 독립적인 반복 테스트가 필요합니다.

## 부하 테스트 요청 로그 비활성화 후 변화

fn-knock에서 루프백 출발지의 요청 로그를 비활성화한 후, 바로 이전의 로그 활성화 실행과 비교한 변화는 다음과 같습니다.

| 동시 연결 | 처리량 변화 | P99 변화 | 평균 지연 시간 변화 |
| ---: | ---: | ---: | ---: |
| 64 | `−4.06%` | `−13.52%` | `+0.67%` |
| 256 | `−0.72%` | `−10.63%` | `−10.08%` |
| 512 | `+0.32%` | `−6.83%` | `−5.03%` |

동시 연결 512에서 처리량 차이는 `0.32%`에 불과해 측정 변동으로 볼 수 있습니다. P99는 `6.83%`, 평균 CPU 사용량은 `0.96%`, 고부하 평균 RSS는 `5.39%` 감소했습니다. 이 실행에서는 총 593,792개의 요청을 전송했으며 접근 로그 증가량은 0 byte였습니다.

따라서 이 시나리오에서 부하 테스트 요청 로그는 주요 처리량 병목이 아니었습니다. 비활성화의 주된 가치는 RPS를 크게 높이는 것이 아니라 디스크 쓰기와 리소스 변동을 줄이는 데 있습니다. 운영 환경에서 루프백 또는 신뢰할 수 있는 출발지 요청을 기록할지는 감사 요구 사항, 저장 비용 및 문제 해결 방식에 따라 결정해야 합니다.

## 관리 API 경로는 참고용 데이터

이번 테스트에서는 제어 영역의 대략적인 리소스 위치를 확인하기 위해 fn-knock `7998` 관리 API의 readiness 경로도 측정했습니다.

| 경로 | 요청 내용 | 처리량 | P99 | 서비스 CPU | 고부하 평균 RSS |
| --- | --- | ---: | ---: | ---: | ---: |
| fn-knock 게이트웨이 `7999` | HTTPS 404, CIDR 판단 및 라우팅 | 13,026 req/s | 498.68 ms | 5.81코어 | 153.4 MiB |
| 다른 제품 | HTTPS 404 | 4,642 req/s | 573.10 ms | 4.37코어 | 325.6 MiB |
| 관리 API `7998` | 게이트웨이 상태 확인을 포함한 HTTP readiness | 5,157 req/s | 162.46 ms | 2.01코어 | 169.3 MiB |

`7998`은 제어 영역이며 readiness 요청은 `7999`의 HTTPS 게이트웨이 데이터 영역과 동등하지 않습니다. 이 수치로 리버스 프록시 용량을 추론할 수 없으며 관리 API를 애플리케이션 트래픽 진입점으로 사용해서도 안 됩니다. 공개 방식과 보안 경계는 [OpenAPI: 관리 API 공개와 AI Agent](/ko/guide/openapi)를 참고하세요.

## 결과 해석 방법

1. **이번 요청 모델에서는 fn-knock의 효율이 더 높았습니다.** 동시 연결 512의 안정 실행에서 처리량은 다른 제품의 약 `2.81×`였고 P99는 더 낮았으며 CPU 코어당 처리량은 `110.89%` 높았습니다.
2. **동시 연결을 늘린다고 유효 용량이 반드시 증가하는 것은 아닙니다.** fn-knock는 동시 연결 64 부근에서 이미 처리량이 정체되었고 추가 동시 연결은 주로 대기 지연을 늘렸습니다.
3. **메모리 결과는 장시간 테스트로 확인해야 합니다.** fn-knock의 단기 고부하 평균과 최고값이 더 낮았지만 한 번의 테스트는 장기 안정성 검증을 대체할 수 없습니다.
4. **로그 정책은 리소스 변동과 디스크 쓰기에 영향을 줍니다.** 특정 요청 종류의 로그를 비활성화할지는 벤치마크 수치만이 아니라 운영 및 감사 요구 사항에 따라 결정해야 합니다.
5. **제어 영역과 데이터 영역은 분리해서 비교해야 합니다.** `7998` readiness 데이터는 참고용이며 HTTPS 프록시 요청과 직접 순위를 비교할 수 없습니다.

## 측정 범위와 제한 사항

- 두 주요 비교 경로 모두 HTTPS, 동일한 Host 및 미일치 라우트 404를 사용했지만 응답 본문 크기는 달랐습니다. fn-knock는 약 11.5 KiB, 다른 제품은 약 65 B였습니다. fn-knock는 더 큰 응답 본문에서도 더 높은 처리량을 기록했습니다.
- 이번 실행은 TLS, CIDR 판단, 라우트 일치 및 게이트웨이가 직접 생성한 응답 처리를 측정했습니다. 특정 업스트림 애플리케이션은 포함하지 않았으며 임의의 워크로드에 대한 종단 간 성능을 나타내지 않습니다.
- “다른 제품”은 이번에 테스트한 특정 버전과 설정만 의미합니다. 결과를 해당 제품의 다른 버전, 배포 방식 또는 전체 유사 제품 범주로 일반화하면 안 됩니다.
- 하드웨어, 커널, TLS 구현, 인증서, 로그 설정, 연결 재사용, 응답 크기 및 네트워크 경로에 따라 결과가 달라질 수 있습니다. 자신의 배포를 평가할 때는 같은 스크립트로 여러 번 반복 테스트하고 처리량, P99, 오류율, CPU, RSS 및 연결 수를 함께 기록하세요.
- 용량 계획에는 여유가 필요합니다. 꼬리 지연 시간이 중요하다면 이 페이지의 동시 연결 수를 그대로 적용하지 말고 실제 요청 모델에서 허용 가능한 상한을 결정하세요.
