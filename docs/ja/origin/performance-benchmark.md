# パフォーマンスとリソース効率の検証

このレポートは、同一の管理されたテスト環境で fn-knock ゲートウェイと他製品を比較した負荷テストの結果です。特定のバージョン、設定、リクエストモデルにおける相対的な結果を示すものであり、第三者認証や、任意のハードウェアおよび本番トラフィックに対する性能保証ではありません。

## 結果の概要

今回の主な比較対象である HTTPS の未一致ルートでは、fn-knock がスループット、P99 レイテンシ、CPU コアあたりのスループット、メモリ使用量のすべてで良好な結果を示しました。

| 指標 | fn-knock | 他製品 | 結果 |
| --- | ---: | ---: | --- |
| 同時接続 512 のスループット | 13,026 req/s | 4,642 req/s | fn-knock は `2.81×` |
| 同時接続 512 の P99 | 498.68 ms | 573.10 ms | fn-knock が `12.99%` 低い |
| CPU コアあたりのスループット | 2,242 req/s/コア | 1,063 req/s/コア | fn-knock が `110.89%` 高い |
| 高負荷時の平均 RSS | 153.4 MiB | 325.6 MiB | fn-knock が `52.90%` 少ない |

ループバック送信元のリクエストログを無効にしても、fn-knock のスループットに大きな変化はありませんでした。一方、高並行時の P99、CPU、メモリ変動はわずかに改善し、この負荷テストのリクエストによるアクセスログへの書き込みもなくなりました。

## テスト条件

| 項目 | 設定 |
| --- | --- |
| テスト日 | 2026-07-31 |
| 負荷生成ツール | `wrk`、8 スレッド |
| 同時接続数 | 64、256、512 |
| 主なリクエスト | HTTPS、Host は `loadtest.invalid`、どのルートにも一致せず 404 を返す |
| リソース計測 | `pidstat` による対象サービスプロセスの CPU と RSS の平均値 |
| 環境条件 | 負荷生成側と 2 つの対象サービスが同じ 8 コアのテストリソースを共有し、各回で同じツールと同時接続パラメーターを使用 |

この構成はネットワーク経路の差を抑えますが、負荷生成ツールも CPU を使用します。そのため、結果はテスト環境全体の合成上限を示すものであり、専用ハードウェアや実際のインターネット経路におけるサービス単体の絶対容量ではありません。

## スループットとテールレイテンシ

| 同時接続 | fn-knock スループット | 他製品スループット | fn-knock の優位性 | fn-knock P99 | 他製品 P99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64 | 13,529 req/s | 2,992 req/s | `352.14%` | 30.38 ms | 81.52 ms |
| 256 | 12,982 req/s | 4,251 req/s | `205.36%` | 242.29 ms | 272.92 ms |
| 512 | 13,026 req/s | 4,642 req/s | `180.63%` | 498.68 ms | 573.10 ms |

fn-knock は同時接続 64 の時点で約 13.5k req/s に達していました。それ以上同時接続数を増やしても安定スループットは上がらず、主にキュー待ち時間とテールレイテンシが増加しました。他製品では同時接続数を 256 から 512 に増やしたとき、スループットは約 `9.2%` 増えましたが、P99 は約 `110%` 増加しました。両方の経路が、このリクエストモデルにおけるそれぞれの容量転換点に近づいていたことを示します。

## 同時接続 512 でのリソース効率

| 指標 | fn-knock | 他製品 | 解釈 |
| --- | ---: | ---: | --- |
| サービス CPU | 5.81 コア | 4.37 コア | fn-knock は CPU を `33.07%` 多く使用 |
| スループット | 13,026 req/s | 4,642 req/s | fn-knock はリクエストを `180.63%` 多く処理 |
| CPU コアあたりのスループット | 2,242 req/s/コア | 1,063 req/s/コア | fn-knock が `110.89%` 高い |
| 高負荷時の平均 RSS | 153.4 MiB | 325.6 MiB | fn-knock が `52.90%` 少ない |

高並行のテストでは fn-knock の CPU 使用量が多くなりましたが、スループットの増加率は CPU の増加率を大きく上回り、コアあたりの効率も高くなりました。CPU 使用率は低ければよいというものではなく、完了したリクエスト数、テールレイテンシ、エラー率と合わせて評価する必要があります。

## メモリのライフサイクル

| 段階 | fn-knock | 他製品 | 他製品 / fn-knock |
| --- | ---: | ---: | ---: |
| 負荷テスト前 | 58.3 MiB | 121.4 MiB | `2.08×` |
| 高負荷時の平均 | 153.4 MiB | 325.6 MiB | `2.12×` |
| 記録されたピーク | 228.6 MiB | 610.0 MiB | `2.67×` |
| 同じテスト回のクールダウン後 | 132.8 MiB | 201.7 MiB | `1.52×` |

他製品の記録上のピークは 610.0 MiB でした。その後の再テストでは 6 回のタイムアウトが発生し、P99 は一時 1.12 秒に達しました。fn-knock の再テストではタイムアウトがなく、記録済みのメモリピークも更新されませんでした。

短時間の再テストで確認できるのは、高水位と初期的な回収傾向だけです。緩やかな増加、断片化、リークの有無を判断するには、安定したリクエストモデルで 30～60 分以上の継続負荷と複数回の独立した再テストが必要です。

## 負荷テストのリクエストログを無効にした場合

fn-knock でループバック送信元のリクエストログを無効にし、その直前の有効なテスト回と比較した結果は次のとおりです。

| 同時接続 | スループットの変化 | P99 の変化 | 平均レイテンシの変化 |
| ---: | ---: | ---: | ---: |
| 64 | `−4.06%` | `−13.52%` | `+0.67%` |
| 256 | `−0.72%` | `−10.63%` | `−10.08%` |
| 512 | `+0.32%` | `−6.83%` | `−5.03%` |

同時接続 512 でのスループット差は `0.32%` にとどまり、測定上の変動とみなせます。P99 は `6.83%`、平均 CPU 使用量は `0.96%`、高負荷時の平均 RSS は `5.39%` 低下しました。この回では 593,792 リクエストを送信し、アクセスログの増加量は 0 byte でした。

したがって、このシナリオでは負荷テストのリクエストログが主なスループットのボトルネックではありませんでした。無効化の主な効果は RPS の大幅な向上ではなく、ディスク書き込みとリソース変動の削減です。本番環境でループバックまたは信頼済み送信元のリクエストを記録するかどうかは、監査要件、ストレージコスト、トラブルシューティング方法に基づいて決定してください。

## 管理 API の経路は参考値のみ

今回のテストでは、コントロールプレーンのリソース位置を確認するため、fn-knock `7998` 管理 API の readiness 経路も計測しました。

| 経路 | リクエスト内容 | スループット | P99 | サービス CPU | 高負荷時の平均 RSS |
| --- | --- | ---: | ---: | ---: | ---: |
| fn-knock ゲートウェイ `7999` | HTTPS 404、CIDR 判定とルーティング | 13,026 req/s | 498.68 ms | 5.81 コア | 153.4 MiB |
| 他製品 | HTTPS 404 | 4,642 req/s | 573.10 ms | 4.37 コア | 325.6 MiB |
| 管理 API `7998` | ゲートウェイ状態確認を含む HTTP readiness | 5,157 req/s | 162.46 ms | 2.01 コア | 169.3 MiB |

`7998` はコントロールプレーンです。readiness リクエストは `7999` の HTTPS ゲートウェイデータプレーンと同等ではありません。この数値からリバースプロキシ容量を推定することはできず、管理 API をアプリケーショントラフィックの入口として使用してはいけません。公開方法とセキュリティ境界については、[OpenAPI：管理 API の公開と AI Agent](/ja/guide/openapi)を参照してください。

## 結果の読み方

1. **今回のリクエストモデルでは fn-knock の効率が高い結果になりました。** 同時接続 512 の安定したテスト回では、スループットが他製品の約 `2.81×`、P99 は低く、CPU コアあたりのスループットは `110.89%` 高くなりました。
2. **同時接続数を増やしても、有効容量が増えるとは限りません。** fn-knock は同時接続 64 付近ですでにスループットが横ばいとなり、それ以上の同時接続は主にキュー待ち時間を増やしました。
3. **メモリの結果は長時間テストで確認する必要があります。** fn-knock は短時間の平均値とピークが低い結果でしたが、1 回のテストで長期安定性を判断することはできません。
4. **ログ方針はリソース変動とディスク書き込みに影響します。** 特定のリクエストをログ対象外にするかどうかは、ベンチマークの数値だけでなく、運用と監査の要件に基づいて決定してください。
5. **コントロールプレーンとデータプレーンは分けて比較する必要があります。** `7998` readiness のデータは参考値であり、HTTPS プロキシリクエストと直接順位付けすることはできません。

## 測定範囲と制限

- 主な 2 つの比較経路では、HTTPS、同じ Host、未一致ルートの 404 を使用しましたが、レスポンス本文のサイズは異なります。fn-knock は約 11.5 KiB、他製品は約 65 B でした。fn-knock はレスポンス本文が大きい状態でも高いスループットを記録しました。
- 今回のテスト対象は TLS、CIDR 判定、ルート照合、ゲートウェイが直接生成するレスポンスの処理です。特定のアップストリームアプリケーションは含まず、任意のワークロードのエンドツーエンド性能を示すものではありません。
- 「他製品」は、今回テストした特定のバージョンと設定だけを指します。結果をその製品の別バージョン、別のデプロイ方法、または同種製品全体へ一般化しないでください。
- ハードウェア、カーネル、TLS 実装、証明書、ログ設定、接続再利用、レスポンスサイズ、ネットワーク経路によって結果は変化します。自分の環境を評価するときは、同じスクリプトで複数回テストし、スループット、P99、エラー率、CPU、RSS、接続数を同時に記録してください。
- 容量計画には余裕が必要です。テールレイテンシを重視する場合は、このページの同時接続数をそのまま採用せず、実際のリクエストモデルで許容できる上限を決定してください。
